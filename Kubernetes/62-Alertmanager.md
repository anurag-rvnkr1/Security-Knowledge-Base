# Chapter 62 – Alertmanager

## Overview

Alertmanager is a component commonly used with Prometheus to manage alerts after Prometheus alerting rules have detected a condition.

Prometheus answers:

```text
Is something wrong?
```

Alertmanager answers:

```text
Who should be notified?
How should alerts be grouped?
Should duplicate alerts be suppressed?
Should this alert be silenced?
```

A typical architecture is:

```text
                    Kubernetes
                        │
                        ▼
                    Prometheus
                        │
                   Alert Rules
                        │
                        ▼
                   Alertmanager
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
        Email         Slack       PagerDuty
```

Alertmanager is particularly useful in production Kubernetes environments because a single incident can generate hundreds or thousands of related alerts.

For example:

```text
Node Down
   ↓
Pods Unhealthy
   ↓
Services Unavailable
   ↓
High Error Rate
   ↓
High Latency
```

Without alert management, engineers could receive hundreds of notifications for one underlying incident.

Alertmanager helps reduce this noise through:

```text
Grouping
Deduplication
Routing
Silencing
Inhibition
```

# What Is Alertmanager?

Alertmanager is responsible for managing alerts generated by Prometheus-compatible alerting systems.

Its main responsibilities include:

```text
Grouping
Routing
Deduplication
Silencing
Inhibition
Notification
```

It does not normally determine whether a metric condition is true.

That is generally handled by Prometheus alerting rules.

---

# Prometheus vs Alertmanager

Prometheus:

```text
Metrics
   ↓
Query
   ↓
Alert Rule
   ↓
Alert
```

Alertmanager:

```text
Alert
   ↓
Group
   ↓
Route
   ↓
Suppress / Deduplicate
   ↓
Notify
```

Therefore:

```text
Prometheus
=
Detect

Alertmanager
=
Manage + Notify
```

---

# Why Alertmanager?

Suppose a Kubernetes node fails.

One underlying failure could generate:

```text
NodeDown
PodDown
PodNotReady
ServiceUnavailable
HighErrorRate
HighLatency
```

Without Alertmanager:

```text
5 Alerts
↓
5 Notifications
```

With grouping and inhibition:

```text
NodeDown
   ↓
Primary Incident
   ↓
Related Alerts Suppressed
```

This makes incident response much easier.

# Alert Rule

An alert rule defines when an alert should be generated.

Example:

```yaml
groups:

  - name: kubernetes

    rules:

      - alert: HighCPUUsage

        expr: cpu_usage > 0.9

        for: 10m

        labels:

          severity: warning

        annotations:

          summary: "High CPU usage"

          description: "CPU usage has remained above 90% for 10 minutes."
```

---

# `for`

The `for` duration prevents alerts from firing immediately when a condition briefly occurs.

Example:

```yaml
for: 10m
```

means:

```text
Condition becomes true
       ↓
Pending
       ↓
Condition remains true for 10 minutes
       ↓
Firing
```

---

# Alert States

Prometheus alert rules commonly transition through:

```text
Inactive
   ↓
Pending
   ↓
Firing
```

If the condition disappears before the `for` duration:

```text
Pending
   ↓
Inactive
```

# Alert Fingerprint

An alert has a fingerprint derived from its identifying labels.

Conceptually:

```text
Alert Name
+
Labels
=
Alert Identity
```

If the same alert repeatedly arrives with the same identity, Alertmanager can recognize it as the same alert.

---

# Deduplication

Deduplication prevents repeated notifications for the same alert.

Example:

```text
Prometheus
   ↓
HighCPU
   ↓
Alertmanager
   ↓
Notification
```

If Prometheus repeatedly sends the same alert:

```text
HighCPU
HighCPU
HighCPU
HighCPU
```

Alertmanager can avoid sending a new notification for every identical occurrence.

---

# Grouping

Grouping combines related alerts.

Example:

```text
Cluster = production

NodeDown
PodDown
ServiceDown
```

Instead of sending:

```text
3 separate notifications
```

Alertmanager can send:

```text
1 grouped notification
```

---

# Grouping Labels

Example:

```yaml
group_by:
  - cluster
  - namespace
```

Alerts with the same grouping labels can be grouped together.

---

# Example

Alerts:

```text
Alert A:
cluster=prod
namespace=payments

Alert B:
cluster=prod
namespace=payments

Alert C:
cluster=prod
namespace=frontend
```

If:

```yaml
group_by:
  - cluster
  - namespace
```

then:

```text
A + B
```

can form one group.

```text
C
```

forms another group.

---

# `group_wait`

`group_wait` controls how long Alertmanager waits before sending the first notification for a new group.

Example:

```yaml
group_wait: 30s
```

This allows additional related alerts to arrive before the first notification.

---

# `group_interval`

`group_interval` controls how long Alertmanager waits before sending updates for an existing group.

Example:

```yaml
group_interval: 5m
```

---

# `repeat_interval`

`repeat_interval` controls how often an alert group can be re-notified while it remains active.

Example:

```yaml
repeat_interval: 4h
```

---

# Group Timing

Conceptually:

```text
First Alert
    ↓
group_wait
    ↓
First Notification
    ↓
Additional Alerts
    ↓
group_interval
    ↓
Updated Notification
```

For a persistent alert:

```text
repeat_interval
```

controls repeated reminders.

# Silence

A silence temporarily prevents notifications for alerts matching specified criteria.

Example:

```text
Maintenance Window
       ↓
Create Silence
       ↓
Matching Alerts Suppressed
```

---

# Why Silencing?

Suppose:

```text
Planned Database Maintenance
```

During maintenance, alerts are expected.

Instead of receiving:

```text
DatabaseDown
DatabaseConnectionFailure
HighErrorRate
```

create a temporary silence.

---

# Silence Matchers

A silence can match labels.

Example:

```text
cluster=production
service=database
```

This suppresses matching alerts for the specified period.

---

# Silence Duration

Silences should have:

```text
Start Time
End Time
Reason
Creator
```

Avoid indefinite silences unless there is a strong operational reason.

---

# Inhibition

Inhibition suppresses alerts when another alert is already active.

Example:

```text
NodeDown
   ↓
PodDown
   ↓
ServiceDown
```

If:

```text
NodeDown
```

is firing, related PodDown alerts may be inhibited.

---

# Inhibition vs Silence

### Silence

```text
Human explicitly suppresses matching alerts
```

### Inhibition

```text
One active alert suppresses another related alert
```

---

# Example

```text
NodeDown
    │
    ├── PodDown
    ├── PodDown
    └── ServiceUnavailable
```

Configure:

```text
NodeDown
   ↓
Inhibit PodDown
```

This reduces alert noise.

---

# Inhibition Rules

An inhibition rule typically defines:

```text
Source Matcher
Target Matcher
Equal Labels
```

Conceptually:

```yaml
inhibit_rules:

  - source_matchers:
      - alertname="NodeDown"

    target_matchers:
      - alertname="PodDown"

    equal:
      - cluster
      - node
```

Exact syntax depends on the Alertmanager version.

# Alert Fatigue

Alert fatigue occurs when engineers receive too many alerts.

Symptoms:

```text
Hundreds of Notifications
Repeated Alerts
Non-Actionable Alerts
Ignored Alerts
```

This is dangerous.

---

# Causes of Alert Fatigue

Common causes include:

```text
Too Many Alerts
Low Thresholds
No Grouping
No Inhibition
No Deduplication
Poor Alert Design
Informational Alerts Sent to Pager
```

---

# Alert Hygiene

Good alerting should follow:

```text

Relevant
Specific
Stable
```

# Actionable Alerts

An alert should require some action.

Bad:

```text

```

if nothing needs to be done.

Better:

```text

```

when sustained CPU saturation creates a meaningful risk.

|---|---|---|

# Chapter Summary

Alertmanager is responsible for managing alerts after they are generated by Prometheus alerting rules.

The overall workflow is:

```text
Metric
 ↓
PromQL
 ↓
Alert Rule
 ↓
Prometheus
 ↓
Alertmanager
 ↓
Grouping
 ↓
Routing
 ↓
Deduplication / Inhibition
 ↓
Receiver
 ↓
Notification
```

The most important Alertmanager capabilities are:

```text
Grouping
Routing
Deduplication
Silencing
Inhibition
Notification
```

Grouping combines related alerts.

Deduplication prevents repeated notifications for the same alert identity.

Routing determines where alerts should go.

Silencing temporarily suppresses matching alerts.

Inhibition suppresses secondary alerts when a related higher-level alert is firing.

Important timing settings are:

```text
group_wait
group_interval
repeat_interval
```

A production alert should contain useful metadata:

```text
severity
team
cluster
namespace
service
summary
description
runbook_url
dashboard_url
```

A mature alerting strategy follows:

```text
Actionable Alerts
+
Clear Ownership
+
Good Severity
+
Grouping
+
Inhibition
+
Runbooks
+
Secure Notifications
```

The most important principle is:

> **Alerting should help engineers respond to real incidents, not simply report every abnormal metric. A good Alertmanager design turns many low-level signals into a small number of meaningful, actionable notifications.**
