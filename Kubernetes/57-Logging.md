# Chapter 57 – Logging

## Overview

Logging is one of the most important observability capabilities in Kubernetes.

Logs provide information about:

```text
What happened?
When did it happen?
Which application was involved?
Which Pod was affected?
Which Node was involved?
What error occurred?
```

A Kubernetes environment can generate logs from multiple layers:

```text
Application
    ↓
Container
    ↓
Pod
    ↓
Node
    ↓
Kubelet
    ↓
Container Runtime
    ↓
Kubernetes Control Plane
    ↓
Audit System
```

A production logging architecture should therefore provide:

```text
Collection
    ↓
Aggregation
    ↓
Parsing
    ↓
Enrichment
    ↓
Storage
    ↓
Search
    ↓
Analysis
    ↓
Alerting
```

# What Is Logging?

Logging is the process of recording events generated by software and infrastructure.

Example:

```text
2026-08-12T09:20:11Z
ERROR
Database connection failed
```

Logs provide historical information about system behavior.

---

# Why Logging Matters

Logs help with:

```text
Troubleshooting
Debugging
Security Monitoring
Incident Response
Performance Analysis
Auditing
Compliance
Application Monitoring
```

Without logs:

```text
Application Failure
      ↓
Unknown Cause
```

With logs:

```text
Application Failure
      ↓
Logs
      ↓
Error
      ↓
Root Cause
```

# Container Logs

A container normally writes application output to:

```text

```

The container runtime captures these streams.

# Standard Output

Example:

```python
print("Application started")
```

This can appear in container logs.

# Standard Error

Errors can be written to:

```text

```

```text

```

# Pod Logs

A Pod may contain one or more containers.

Example:

```text
Pod
├── frontend
├── proxy
└── metrics
```

Each container can generate separate logs.

---

# `kubectl logs`

View logs:

```bash
kubectl logs <pod>
```

Example:

```bash
kubectl logs nginx
```

---

# Logs From a Namespace

```bash
kubectl logs -n production <pod>
```

---

# Follow Logs

Use:

```bash
kubectl logs -f <pod>
```

This continuously streams new log entries.

---

# Tail Logs

Example:

```bash
kubectl logs --tail=100 <pod>
```

This retrieves the latest 100 lines.

---

# Logs Since a Time Period

Example:

```bash
kubectl logs --since=1h <pod>
```

This retrieves logs from approximately the previous hour.

---

# Logs Since a Timestamp

You can use:

```bash
kubectl logs \
  --since-time="2026-08-12T08:00:00Z" \
  <pod>
```

---

# Previous Container Logs

If a container crashed and restarted:

```bash
kubectl logs <pod> --previous
```

This is extremely useful for crash investigation.

---

# Why `--previous` Matters

Consider:

```text
Container
   ↓
Crash
   ↓
Restart
```

Current logs may only show the new process.

The previous logs can reveal:

```text
Why the previous process crashed
```

---

# Multi-Container Pods

For:

```text
Pod
├── app
└── sidecar
```

specify the container:

```bash
kubectl logs <pod> -c app
```

or:

```bash
kubectl logs <pod> -c sidecar
```

---

# All Containers

You can retrieve logs from all containers:

```bash
kubectl logs <pod> --all-containers=true
```

---

# Init Container Logs

For an Init Container:

```bash
kubectl logs <pod> -c <init-container>
```

This is useful when Pod initialization fails.

---

# Timestamps

Display timestamps:

```bash
kubectl logs <pod> --timestamps
```

Timestamps help correlate events across systems.

---

# Label-Based Log Retrieval

Depending on the workload, logs can be retrieved using selectors.

Example:

```bash
kubectl logs \
  -l app=backend \
  --all-containers=true
```

This is useful for collecting logs from multiple Pods.

# Structured Logging

Structured logs store information in a machine-readable format.

Example:

```json
{
  "timestamp": "2026-08-12T09:40:10Z",
  "level": "ERROR",
  "service": "payment",
  "request_id": "abc123",
  "error": "database_timeout"
}
```

---

# Advantages of Structured Logging

Structured logs are easier to:

```text
Search
Filter
Parse
Correlate
Aggregate
Analyze
```

---

# JSON Logging

JSON is commonly used for structured logs.

Example:

```json
{

  "message": "User authenticated",
  "user_id": "user-123"
```

```text

   ↓
```

# Elasticsearch vs Loki

| Feature | Elasticsearch | Loki |
|---|---|---|

| Typical Use | Full-text analytics | Kubernetes/Grafana logging |

# Log Retention

Retention defines how long logs are stored.

Example:

```text
Application Logs → 30 days
Security Logs → 90 days
Audit Logs → 1 year
```

Actual retention should follow organizational, operational, and regulatory requirements.

---

# Log Rotation

Without rotation:

```text
Log File
   ↓
Grows Forever
   ↓
Disk Full
   ↓
Node Problems
```

Log rotation prevents unbounded growth.

---

# Log Rotation Strategy

Conceptually:

```text
app.log
app.log.1
app.log.2
app.log.3
```

Older files can be compressed or removed according to policy.

---

# Why Log Rotation Matters

Uncontrolled logs can cause:

```text
Disk Exhaustion
Node Instability
Application Failure
```

---

# Log Volume

A production cluster can generate huge amounts of logs.

Example:

```text
100 Pods
×
10 MB/hour
=
1 GB/hour
```

Over 30 days:

```text
1 GB × 24 × 30
=
720 GB
```

This is why logging cost and retention must be designed carefully.

---

# Log Sampling

Sampling reduces log volume.

Instead of storing every repetitive event:

```text
10,000 identical events
```

you may retain representative information.

Sampling must be used carefully for:

```text
Security Events
Audit Events
Critical Errors
```


```json
}
```

```text

```

or:


# Backpressure

If the log destination is slow:

```text
Application
 ↓
Huge Log Volume
 ↓
Collector
 ↓
Backend Slow
```

the system must handle backpressure.

Otherwise:

```text
Memory Growth
Disk Growth
Dropped Logs
```

can occur.

# Dropped Logs

# Node Agent vs Sidecar

| Approach | Advantage | Disadvantage |
|---|---|---|

### Answer

Containerized applications commonly use:


For legacy applications that only write files, a sidecar or another collection mechanism may be appropriate.
