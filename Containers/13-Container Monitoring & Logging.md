# Chapter 13 – Container Monitoring & Logging

## Overview

Container Monitoring and Logging is the continuous process of collecting, analyzing, visualizing, and alerting on operational and security-related information generated by containerized applications and the underlying infrastructure. It enables organizations to maintain application health, identify performance bottlenecks, troubleshoot failures, detect security incidents, and ensure service reliability.

Unlike traditional servers, containers are **ephemeral**—they can be created, restarted, scaled, or removed within seconds. Because of this dynamic nature, monitoring and logging must be automated, centralized, and capable of tracking rapidly changing workloads.

Container Monitoring and Logging is a fundamental component of:

- Docker
- Kubernetes
- DevOps
- DevSecOps
- Site Reliability Engineering (SRE)
- Cloud Security
- Observability
- Incident Response

Without effective monitoring and logging, diagnosing production issues and security incidents becomes significantly more difficult.

# Monitoring vs Logging

| Monitoring | Logging |
|------------|---------|
| Tracks current system health | Records events over time |
| Uses metrics | Uses log messages |
| Real-time visibility | Historical analysis |
| Detects anomalies | Explains what happened |
| Supports alerting | Supports troubleshooting |

Monitoring and logging complement each other and should be used together.

## How It Works

Container Monitoring and Logging operate continuously throughout the lifecycle of a containerized application. Every container generates metrics and logs while it is running. Monitoring systems collect numerical metrics such as CPU and memory usage, while logging systems capture timestamped events generated by applications, containers, and the underlying infrastructure.

Together, these systems provide real-time visibility into application health, performance, and security.

# Golden Signals

Google's **Golden Signals** are four key metrics for monitoring user-facing services.

```
Latency

↓

Traffic

↓

Errors

↓

Saturation
```

### Latency

How long requests take to complete.

Examples:

- API response time
- Database query time

---

### Traffic

Measures demand on the application.

Examples:

- Requests per second
- Transactions per minute
- Active users

---

### Errors

Measures failed operations.

Examples:

- HTTP 500 responses
- Authentication failures
- Database errors

---

### Saturation

Measures resource exhaustion.

Examples:

- CPU utilization
- Memory consumption
- Disk usage
- Queue length

Monitoring these four signals provides an effective high-level view of application health.

# Best Practices

### 1. Centralize Logs

Avoid storing logs only on individual hosts.

Centralized logging improves:

- Troubleshooting
- Searchability
- Compliance
- Disaster recovery

---

### 2. Monitor Golden Signals

Track:

- Latency
- Traffic
- Errors
- Saturation

These metrics provide an effective overview of service health.

---

### 3. Monitor Resource Limits

Continuously monitor:

- CPU
- Memory
- Disk
- Network

Unexpected increases often indicate application issues.

---

### 4. Configure Alerts Carefully

Alert only on meaningful conditions.

Poorly configured alerts can create alert fatigue and reduce operational effectiveness.

---

### 5. Use Structured Logging

Prefer structured formats such as JSON over free-form text.

Structured logs are easier to:

- Search
- Parse
- Correlate
- Analyze

---

### 6. Include Correlation IDs

For distributed applications:

```
Request

↓

Frontend

↓

Backend

↓

Database
```

Use correlation IDs to trace a request across multiple services.

---

### 7. Retain Logs Appropriately

Define retention policies based on:

- Operational requirements
- Compliance obligations
- Storage capacity
- Organizational policy
